# Step 5 — CHECK

Two spawns per execution unit — the whole task under Small/Medium scope, the current phase under Large — run **in parallel** (both Task calls in one message), each in a fresh context:

- **`crafter-checker`** judges drift and verification evidence against the contract. It gets the full task context.
- **`crafter-reviewer`** reviews the code from the change range alone. It gets no task context of any kind.

There is no separate verification spawn.

**Extension skill check — only when `--ext` is active.** Without the flag, skip this paragraph entirely. With it, check for compatible extension skills discovered at startup (see `{CRAFTER_HOME}/rules/do/extension-skills.md`) whose `When-Applies` matches the work being checked, and include their names and capabilities in the context passed to the **Checker** as supplemental context — never to the Reviewer. Extension skill findings are advisory only and cannot replace either report. See `rules/do-workflow.md` → `### Extension-skill supplemental-only invariant`.

## Full pass

1. Spawn both agents in parallel:
   - The `crafter-checker` in mode `full pass`, with: the approved contract (including its seams and verification evidence), accepted deviations, the Implementer's per-step report **including its Evidence section**, the list of changed files, a mention of `{CRAFTER_DIR}/ARCHITECTURE.md` if available, and — under `--auto` — the `--auto` indication. Remind it in the task prompt: "Write your report as plain text in your response. Do not create any files."
   - The `crafter-reviewer` with **only**: the range `working tree` (the unit stays uncommitted until Step 6b), the line `repository: {PROJECT_PATH}` when `PROJECT_PATH` is not `.`, the report-language line and the no-filler rule (`rules/delegation.md` § Report Language), and the skill directives block. No contract, no Implementer report, no file list, no ARCHITECTURE.md, no `--auto` indication, no extension context.

   Neither agent gets file contents — both read files themselves.
2. Initialize the fix-loop iteration count at 0.

**Relay both reports verbatim.** Reproduce the Checker's report sections — on a full pass **Drift findings** and **Contract deviations**, on a delta pass **Prior findings status**, **New drift findings**, **Not re-checked**, and **Widening required** — and the Reviewer's summary line and **Findings** list as-is — relay each finding list verbatim, exactly as the agent wrote it, never reformat it into tables or prose or re-shape its items. After the reports, state the recommendation. This relay happens on **every** pass, before any commit, regardless of severity.

**Finding owners.** Code findings (severity Critical / Major / Minor / Suggestion, numbered `R<n>`) come from the Reviewer; drift findings (numbered `D<n>`, with the plan step they belong to) come from the Checker. The orchestrator does not merge or deduplicate finding blocks by judgment — an overlapping block from each agent stays two findings. Both agents number from `1` on every pass, so a finding's identity is its number **plus the pass it came from** — the full pass is pass 0, fix-loop iteration *k*'s re-check is pass *k*. Whenever findings from different passes appear together (the open set, the inputs to the Implementer and the Checker, the send-back limit), write them pass-qualified as `<number>@<pass>`, e.g. `R1@0`, `R1@2`, `D3@1`.

## Acting on the reports

**Buffered-finding carve-out (`--auto`).** Under `--auto`, a finding recorded as a buffer entry counts as **handled, not open**, for every progress condition in this step — the step tick (sub-step 1), the gate tick (sub-step 7), and the transition to Step 6b (sub-step 9). Two routes lead there: a drift finding the Checker routed to `gap` or `uat`, and a code finding the Implementer left unfixed in the fix loop and tagged `[gap-worthy]` or `[uat-worthy]`.

1. **Batch-tick.** Check off the unit's steps in one pass over the task file. A step stays **unchecked** only when harmful, scope, or plan-obsoleting drift is attributed to it in the **Step** field of the Checker's drift-finding header — subject to the **buffered-finding carve-out** above. Reviewer findings carry no step attribution, so they never block a step tick; an open code finding gates only the Check line (sub-step 7), and resume re-enters at that pending gate. The orchestrator remains the only writer of the task file.
2. **Minor issues — STOP for a user decision; Suggestion issues and beneficial local drift — auto-proceed.** For Minor findings, ask the user to choose: **fix all**, **pick numbers** to fix, or **defer all**. Chosen Minors enter the fix loop like Critical/Major findings; when the same pass also has Critical/Major findings or harmful drift, ask in the same stop. Record each deferred Minor as `Decision (Tech Debt — user-deferred): Minor — <description>`, each Suggestion as `Decision (Tech Debt — auto-recorded): Suggestion — <description>`, and beneficial local drift as `Decision (Orchestrator Accepted)`, in the task file's `## Decisions` section. If nothing remains to fix, complete sub-steps 7–9 below and continue. Suggestions never cause a wait; the verbatim relay above already gave the user full visibility. **Under `--auto`:** do not ask — record Minor findings as `Decision (Tech Debt — auto-recorded)` entries like Suggestions and continue without waiting.
3. **Critical or Major code findings, or harmful drift — STOP.** Present the reports and wait for the user's response, then enter the fix loop. There is no "proceed anyway" for those. **Under `--auto`:** do not wait — every Critical and Major code finding enters the fix loop directly; harmful drift is routed by the Checker's classification table: `auto-fixable` enters the fix loop; `gap` and `uat` become buffer entries and the run continues; `escape-hatch` exits with state via the **Ad-hoc escape hatch** (`rules/do-workflow.md` → `#### Ad-hoc escape hatch`).

   **Reachability send-back — the orchestrator never downgrades a severity.** It has no code context; only the Reviewer assigns or lowers a severity. This applies to **any new Critical or Major code finding at fix-loop entry** — from the first pass or from a re-check re-entering via **Fix loop** sub-step 5. A finding that names neither a trigger nor one of the Reviewer's three reachability states is **sent back to the `crafter-reviewer`** as a `reachability check`: the same range plus that one finding block, still with no task context. Findings that already name a trigger, or already say "cannot determine — severity kept", go straight to the fix loop. The send-back is a Reviewer-only pass: no Implementer spawn, no code change, so it does **not** increment the fix-loop iteration count and leaves the 5-iteration cap untouched. At most one send-back per finding, tracked by its pass-qualified number from the relayed report — no separate bookkeeping file; whatever the Reviewer returns the second time is final; a finding it lowers to Minor gets the Minor choice from sub-step 2 (fix / defer), auto-recorded under `--auto` like any Minor. It happens **after** the verbatim relay of the report that triggered it, and the report it returns is relayed verbatim too. Identical interactive and under `--auto`.
4. **Scope drift** — stop and ask the user whether to accept the drift, revise scope, or replan. If accepted, append a `Decision (User Accepted)` entry. **Under `--auto`:** do not ask — route the drift by the Checker's classification table (`gap` / `uat` / `auto-fixable` / `escape-hatch`), recording `gap`/`uat` as buffer entries and continuing; `auto-fixable` enters the fix loop and `escape-hatch` exits with state.
5. **Plan-obsoleting discovery** — return to Step 3 with the new discovery. **Under `--auto`:** the Checker always routes it to `escape-hatch` — exit with state via the **Ad-hoc escape hatch** (`rules/do-workflow.md` → `#### Ad-hoc escape hatch`) instead of returning to Step 3.
6. **`--auto` routing — two owners.** Code findings are routed by the orchestrator's severity mapping: Critical/Major → fix loop; Minor/Suggestion → auto-recorded as tech debt per sub-step 2. Drift findings are routed by the Checker's classification table — vocabulary `gap` / `uat` / `auto-fixable` / `escape-hatch`; the per-branch handling is in sub-steps 3–5. A code finding the Implementer leaves unfixed in the fix loop and tags `[uat-worthy]` / `[gap-worthy]` becomes a buffer entry via the `crafter-buffer` skill and counts as handled under the carve-out.
7. **Tick the Check gate.** Once the pass closes clean — every step of the unit ticked and no Critical or Major code finding, harmful drift, or Minor finding the user chose to fix, open — change the unit's `- [ ] Check` gate line to `- [x] Check` in the task file. The **buffered-finding carve-out** above applies.
8. **Record decisions.** Record any notable decisions in the task file's `## Decisions` section per `{CRAFTER_HOME}/rules/task-lifecycle.md`.
9. **Continue to Step 6b** — only after sub-steps 7 and 8, and only when no Critical or Major code findings, no Minor findings the user chose to fix, and no unresolved drift remain. The **buffered-finding carve-out** above applies.

Sub-steps 7–9 are mandatory whenever leaving Step 5 toward Step 6b, regardless of which branch led there.

## Fix loop (Critical/Major, chosen Minor, and harmful drift)

1. **Increment the iteration count at loop entry** — the first pass is iteration 1. If the incremented value would exceed 5, do NOT start that pass. Present all remaining Critical/Major, chosen Minor, and harmful-drift findings and ask the user to choose one of:
   - **(a) manual override** — authorize iteration beyond the cap; re-enter the loop only on explicit user instruction.
   - **(b) accept-without-commit** — accept the unresolved findings and proceed without committing; record a Decision noting that the green-commit invariant is deliberately broken here.
   - **(c) replan-and-abort** — abandon the current work and return to planning.

   Under `--auto`, do NOT present the (a)/(b)/(c) choice — exit with state per `rules/do-workflow.md` → `### --auto (unattended orchestration)`. Do not continue to sub-step 2 until the user has chosen (non-`--auto`).
2. Spawn the `crafter-implementer` agent with: the list of open findings — Critical/Major code findings, chosen Minor findings, and harmful drift (pass-qualified finding number, severity or classification, file, line, description) — the approved contract, and accepted deviations. Under `--auto`, also pass the `--auto` indication and this instruction: "A finding that code cannot resolve here (it needs a live environment, manual interaction, or work outside the contract) may be left unfixed; list it under deviations/discoveries with its finding number, tagged `[uat-worthy]` or `[gap-worthy]`." The Implementer reads files itself and re-runs the relevant checks.
3. Receive the fix summary. If the Implementer reports a blocker, stop and discuss with the user. Under `--auto`, a code finding it left unfixed and tagged `[uat-worthy]` / `[gap-worthy]` becomes a buffer entry per **Acting on the reports** sub-step 6.
4. **Re-check — both agents in parallel.**
   - The `crafter-checker` in mode `delta pass`, with the approved contract, only the files the fix changed, **every prior open finding** — drift and code alike — and, under `--auto`, the `--auto` indication. It reports `resolved` / `still present` / `partially resolved` for each, with evidence, plus any new drift in the delta and whether widening is needed.
   - The `crafter-reviewer` on the range `working tree` restricted to the files the fix changed, with the same inputs as on the full pass and nothing else. Every finding block it reports counts as a new code finding.
5. Relay both reports verbatim — for the Checker that includes **Prior findings status**, **New drift findings**, **Not re-checked**, and **Widening required**. The open set is now: the prior findings the Checker did not report `resolved`, plus the new findings from both reports. New Minor findings get the sub-step 2 choice; new Critical/Major code findings go through the reachability send-back. If no Critical/Major code findings, no chosen Minor findings, and no harmful drift remain, the loop is closed → run sub-steps 7–9 of **Acting on the reports** → Step 6b. Otherwise go back to sub-step 1 with the findings that remain.
6. **Widening.** If the Checker reports that the fix touched files outside the delta, the next pass is a **full pass for both agents** — the Checker in mode `full pass` with the full-pass inputs (including the `--auto` indication when set) and the Reviewer on the unrestricted working tree — then delta re-checks resume. The iteration count and the 5-cap are unaffected.
